# Traceability Matrix

The whole-project map from **spec → code**. These matrices are the *instance* of a broader **bidirectional traceability graph** — business objective → feature → use case / FR → design → code → tests, with business rules and quality attributes as cross-cutting layers — described as one picture in [methodology.md, *The traceability model*](methodology.md#the-traceability-model). This file is where that model is recorded and verified. At a glance:

```text
BO ──served by──▶ Feature ──realized by──▶ Use Case ───▶ design → code → test
                     │                   └─▶ non-UC FR ─▶ design → code → test
                     │
                     └─ the objective attaches ONCE, here at the feature; UC / FR below inherit it

off-spine overlays — each hangs off one node, a different question than "is it built?":
   BO ──measured by──▶ Success Metric ──▶ evaluation route   (was it ACHIEVED? — post-deployment, not a code test)
   Use Case / FR ──honors──▶ Business Rule                   (what policy bounds it? — cited, never restated)
   Quality Attribute ──▶ Quality Scenario (QS) ──▶ test      (NFRs verified in parallel, never via a use case)
   Risk ──▶ mitigation / acceptance                          (threatens the BO; off the build line)
```

The matrices below **are** this graph, sliced into tables — on two primary realization axes (functional and non-functional), plus a cross-cutting coverage layer for the off-spine requirement types:

- **[Functional traceability](#functional-traceability-matrix)** — one row per use case (`UC-<AREA>-<slug>`), linking it to the cross-cutting functional requirements it depends on and the actual frontend/backend/test artifacts that implement it. This is how Claude (and you) find the right code from a requirement, and — via the separate **Build** and **Verify** columns — see at a glance **which use cases are built and which of those are actually test-verified**. The two states are tracked independently on purpose: a built-but-untested use case stays visibly unverified instead of being absorbed into a single "done" symbol. Its companion, the **[non-use-case FR matrix](#non-use-case-fr-traceability)**, gives each cross-cutting `FR-<AREA>-*` its own realization row — because a non-use-case FR is a *functional* requirement node in its own right (sibling of the use case), not just a dependency annotation on UC rows.
- **[Non-functional traceability](#non-functional-traceability-matrix)** — one row per quality attribute (`PER-*`, `SEC-*`, `ROB-*`, …), mapping it to the architecture-of-record's quality scenario (`QS-<slug>`) that operationalizes it and the test that verifies it.
- **[Cross-cutting coverage](#bo-measurement-matrix)** — the layers the two realization matrices don't capture, in three matrices. Each business objective (`BO-*`) traces *forward to outcome* through its success metric (`SM-<slug>`) — was the objective **achieved**, not merely built? — in the **[BO measurement matrix](#bo-measurement-matrix)**. Each risk (`RI-*`) traces forward to the mitigating requirement(s)/decision that responds to it, or is consciously accepted, in the **[risk coverage matrix](#risk-coverage-matrix)**. And each business rule (`BR-*`) — the third off-spine layer — traces *backward* to the complete set of requirements that enforce it in the **[business-rule enforcement index](#business-rule-enforcement-index)**: because a `BR-*` is *cited, never restated*, it carries no realization row, so this index is instead a **generated projection** of the forward citations (the use cases' Business Rules fields, the SRS, and the `QS-<slug>` rows — regenerated and verified by `/spec-build`, never hand-edited), giving the `BR → {UC/FR/QS}` view that change-impact analysis needs.

Together these make this file the single place to ask "is requirement X traced?" for every requirement type on the spine and off it — "is it built and verified?" for functional and non-functional requirements (the two realization matrices), and "is it covered?" for the off-spine types (each `BO-*` traced forward to its outcome metric, each `RI-*` to a mitigation or acceptance, each `BR-*` backward to its enforcers). Note: in this project a **use case is itself a (high-level) functional requirement**, and its "The system …" steps + Associated Information are its detailed functional spec (the SRS's Use Cases section); the SRS's Non-Use Case Functional Requirements "shall" statements capture only the system-level behaviors. The `QS-<slug>` scenario *definitions* (stimulus/response/measure) are owned by the [architecture-of-record](design/architectural-design.md#quality-requirements) and cited here by ID; this file owns the **verification map** (which test proves each scenario, and its state).

**Reading order.** Before those matrices the file opens with a **feature → use case area** map — a vision-level orientation that bridges `requirements/vision-and-scope.md`'s features to the UC areas the functional matrix is keyed to. After it the matrices follow in the order above: the functional matrix and its non-use-case-FR companion, the non-functional matrix, then the three cross-cutting coverage matrices (BO measurement, risk coverage, business-rule enforcement).

## Feature → use case area coverage

`requirements/vision-and-scope.md` lists product **features** (stakeholder-visible **capability themes**); `requirements/use-cases.md` groups behavioral specs into **use case areas** (`UC-<AREA>-*`, each mirroring a backend bounded context). A feature is deliberately **coarser** than an area and **never one-to-one** with one — each theme decomposes into use cases drawn from several areas, and an area can serve more than one feature. This map keeps them aligned without making `vision-and-scope.md` cite UC IDs directly. See [methodology.md](methodology.md), *Features and use case areas — different views, not different fragments*, for why the two are not made 1:1.

The first column lists each feature by its `FEAT-<slug>` ID and name, exactly as defined in `vision-and-scope.md`; the map is **keyed to the ID**, and `/spec-build`'s feature-coverage check verifies the two sets match (every `FEAT-*` has exactly one row here, and every row resolves to a defined feature). The **BOs** column names the business objectives the feature serves; the **UC areas** column names every use-case area whose use cases realize the feature (the area owning the primary surface listed first); and the **Cross-cutting FRs** column names the non-use-case `FR-<AREA>-*` requirements that realize it (an `FR-<AREA>-*` glob denotes that whole family).

This map is the **single anchor for the `BO → feature` edge** and the head of the realization spine: **business objectives attach to the feature, and the use cases and FRs below inherit their objective through it.** Every non-carve-out `BO-*` must be named by at least one feature, and every feature must have at least one realizer (a UC area or a cross-cutting FR). Enabling/substrate features that serve no measurable objective directly show `—` in **BOs** (e.g. `FEAT-administration`, whose `FR-SEC-*` security realizers underpin everything without advancing a single objective); `BO-RAM-research` appears in no row, being the platform-level emergent objective with no single-feature realizer. The complementary *outcome* edge — whether an objective was **achieved**, not just built — lives in the [BO measurement matrix](#bo-measurement-matrix) via its success metrics, not here.

## Functional traceability matrix

> `/design` runs in two beats: it first sets a use case's **Build** to `🔬 Problem-validated` once its challenge loop has firmed the use case (spec fixes looped back), then to `📐 Designed` — filling the **Design** column with the area's design-of-record — when the solution design is approved (trivial use cases reach `📐` in one motion); `/implement` fills the code columns, sets **Build**, and fills **Verify** at the end of its run (Phase 5).

### How to use it

- **One row per use case**, in `UC-<AREA>-<slug>` order, mirroring `requirements/use-cases.md`.
- **Build** — construction state of the code, from the Build legend below (`❌` → `🔬` → `📐` → `🟡` → `✅`). It says nothing about tests; `✅ Built` is a claim about code only.
- **Verify** — whether automated tests exercise and pass for the built behavior, from the Verify legend below. Deliberately **independent of Build**: a `✅ Built` use case with no test reads `🔎 None` here, so "done" can never hide an untested flow. `—` until there is built behavior to verify (Build is `❌`/`🔬`/`📐`). RAM has no frontend automated tests yet (see the matrix note), so a built RAM use case's Verify reflects its **backend** test coverage; that frontend-test gap is recorded once rather than per row.
- **Release:** the release plan, the tag in which the row's code ships, from the Release legend below. Build and Verify say where the work is; Release says when it is planned to be done. It tracks Build only: a shipped row whose Verify is `🔎 None` or `🟡 Partial` keeps its Release, and its missing tests are test debt, visible in Verify and tracked as an issue. Set it when the row is added, and revise it when a use case closes or the scope changes; the pull request that changes a Release cell says why. Scope is not set here: a use case whose `**Status:**` line marks it Deferred or Tabled (see the use-case lifecycle status convention in [`CLAUDE.md`](CLAUDE.md)) is out of the MVP, and its Release cell stays empty. On any other row, an empty cell is unplanned work.
- **FR IDs** — the SRS's non-use-case, system-level functional requirements this use case **depends on / builds upon** (e.g. autosave, validation, real-time collaboration, AI), and, where relevant, the External Interface Requirements (`SI-*`) that carry the use case's interface detail (export formats/fidelity, import allowlist/extraction). The use case's own "The system …" steps are its primary acceptance criteria; this column points to the reusable cross-cutting subsystems behind it. **This column is deliberately non-exhaustive — read it as additive over a universal baseline, not as the complete FR set for the row.** The most universal behaviors — RBAC (`FR-SEC-*`) and authorship metadata (`FR-HIS-authorship-metadata`) — apply to **nearly every** row, so they are an **implicit baseline omitted from every cell** to reduce noise: their absence from a row is **never informative** — it never means the use case escapes authorization or authorship. The column therefore lists only the *additional* cross-cutting FRs a use case draws on **beyond** that baseline, and **`—` means "none beyond the baseline"** (the use case is otherwise self-contained — its own steps are the whole spec), **not** "this use case has no security or authorship dimension." Section locking is part of the editing use cases' own steps (governed by `BR-edit-lock-required` / `BR-lock-expiry`), not a separate FR.
- **Design** — the area's design-of-record (`design/<area>.md`, optionally anchored to the use case's sequence diagram under *Sequence*, the one per-use-case heading the doc carries) once `/design` has written it and its pull request has merged; `—` until then. A single area doc covers every use case in its area, so rows in the same area cite the same file.
- **Frontend / Backend / Tests** — concrete artifacts (`file_path` or component/class names) once built; `—` until then.
- **Extension coverage (convention).** Because tests are tagged to the **whole use case** — there are no per-step or per-extension IDs — the **Tests** cell names *which extensions* a test exercises, e.g. `…AddEvaluation… + matching extensions (E1,E3); E2 untested`. This keeps edge-case coverage visible: a `✅ Verified` row whose negative/exception flows are only partly tested shows `🟡 Partial` in Verify with the gap spelled out in Tests. `/sync-check` flags any `✅ Built` use case whose count of negative-path tests is below its number of extensions (a heuristic that surfaces likely-undertested exception behavior). Back-filling the per-extension annotation across the already-built use cases is a `/sync-check` sweep, not a precondition for the convention.
- When a use case is added to `requirements/use-cases.md`, add its row here (Build `❌ Not started`, Verify `—`, and a Release value). `/design` advances Build to `🔬 Problem-validated` once the use case is firmed, then `📐 Designed` when the solution design is approved; when `/implement` finishes it, set Build, fill Verify, and fill the code columns.

### Build legend

| Symbol | Meaning |
|--------|---------|
| ❌ Not started | No design, no code; the use case is unexamined. |
| 🔬 Problem-validated | `/design`'s challenge loop has run against the use case — ambiguities, contradictions, and assumptions that break against the code surfaced and looped back into the spec; the problem statement is firm. No solution design yet. (The `❌ → 🔬` transition **is** a recorded challenge event; its evidence is the spec diff that produced it.) |
| 📐 Designed | Solution approved — the area's `design/<area>.md` is written (`/design`) and approved by merging its pull request, with the questions-test result in the pull request description; not yet coded. |
| 🟡 In progress | Partially built (e.g., backend complete, frontend pending). |
| ✅ Built | Code complete for the use case's flow. **Makes no claim about tests** — see the Verify column. |

### Verify legend

| Symbol | Meaning |
|--------|---------|
| ✅ Verified | Automated test(s) exercise the built behavior — main flow and extensions — and pass. |
| 🟡 Partial | Some flows/extensions are tested; others are not (the Tests cell names the gap). |
| 🔎 None | Built, but no (or insufficient) automated test exists. |
| — | Nothing built to verify yet (Build is `❌`, `🔬`, or `📐`). |

### Release legend

| Value | Meaning |
|-------|---------|
| ≤ v1.5.0 | Shipped before the release plan began (planning started with the work left after `v1.5.0`). |
| v1.6.0, v1.7.0, … | The planned release tag. The next tag is the one being worked toward; later tags are the planned order. |
| Later | In scope, not yet scheduled. |
| (empty) | Only on a use case whose `**Status:**` line marks it Deferred or Tabled; that line owns its scope. |

## Non-use-case FR traceability

Non-use-case functional requirements (`FR-<AREA>-*`) are **first-class requirement nodes** — siblings of the use case under each feature (a use case *is* a high-level FR; these are the cross-cutting ones no single use case owns: autosave, validation, AI, templates, glossary invariants, authorship metadata, notifications, security). The functional matrix above records them only as the *FR IDs* **dependency** column on UC rows; this matrix gives each its **own realization** row (design → code → tests → build/verify), so "is `FR-X` built and tested?" has an answer even when no use case carries it. An FR that appears in a UC row's *FR IDs* column is therefore not duplicated here: the UC row records the *UC depends on FR* edge, while this row records the FR's own *FR → design → code → tests* tail. Each FR inherits the business objectives it serves from its **feature** — named inline in the SRS (`_(Part of FEAT-…)_`) and in the [feature → use case area map](#feature--use-case-area-coverage)'s **Cross-cutting FRs** column — so this matrix carries no BO column of its own. Same Build, Verify, and Release legends as the functional matrix.

Two conventions keep this from duplicating the other matrices: a cross-cutting FR already verified through a quality scenario (the `FR-SEC-*` ↔ `QS-cross-team-denial`/`QS-unauthenticated-rejection` pair) cites that scenario in **Tests** rather than restating it; and **deferred** non-use-case FRs carry no row until scheduled (mirroring deferred use cases) — `FR-HIS-checkpoint` / `-restore` / `-retention` and `FR-TPL-customize` are post-MVP and omitted here.

## Non-functional traceability matrix

The second axis: **quality attribute → quality scenario → verifying test**. Where the functional matrix above is keyed to the use case and some functional requirements, this one is keyed to the SRS quality attributes (`USE-*`, `PER-*`, `SEC-*`, `AVL-*`, `ROB-*`, `SCA-*`, `INT-*`, `MNT-*`). Each is operationalized by a quality scenario (`QS-<slug>`) in the [architecture-of-record](design/architectural-design.md#quality-requirements) — which owns the scenario *definitions* (stimulus / response / measure) — and verified by a test cited here. This file owns the **verification map** (the *Verifying test* and *State* columns); the arch-of-record's QS table points back here rather than duplicating them.

### How to use it

- **One row per committed quality scenario** in the first table; the `QS-<slug>` cell cites the arch-of-record scenario by ID (definitions live there, not here).
- A quality attribute that no committed scenario yet operationalizes is **not** dropped silently — it goes in the *unpinned tail* table with its verification route, so an untraced NFR is visible rather than forgotten.
- When a new `QS-<slug>` is added to the arch-of-record, add its row here; when `/implement` builds the feature a `❌ Pending feature` row waits on, fill the *Verifying test* and flip the *State*.

## BO measurement matrix

Business objectives (`BO-*`, owned by [vision-and-scope.md](requirements/vision-and-scope.md#business-objectives)) sit at the **head** of the spine — the *why*. The functional and non-functional matrices above answer "is the objective **built**?"; this matrix answers the complementary, post-deployment question "was it **achieved**?" — the outcome → objective backward edge that ISO/IEC/IEEE 29148 calls for and that most projects leave implicit. Each objective's success metric(s) (`SM-<slug>`, defined in `vision-and-scope.md`'s [Success Metrics](requirements/vision-and-scope.md#success-metrics) section and tagged with the objective they measure — a strategic objective may carry several, one per measurable outcome) are recorded here, one row per metric, with its evaluation route and state.

Most routes are **empirical** — survey, system logs, rubric scoring, instructor judgment — **not automatable tests**: objective achievement is *validated after deployment*, not unit-tested, and naming the route keeps that honest rather than implying a code test exists. A platform-level emergent objective carries no metric (the `*(Platform-level emergent objective; …)*` carve-out). `/spec-build`'s **BO-measurement** check flags any non-carve-out `BO-*` with no `SM-<slug>`.
